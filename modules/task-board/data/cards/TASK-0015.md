# TASK-0015 — Refatorar o Web Controller para utilizar Custom Workspaces

## Summary

Eliminar a interface própria do Web Controller e transformá-lo em um publicador de Custom Workspaces do NodeStage.

## Detailed Description

<!-- task-board:description:start -->
O sistema atual do Web Controller deve ser completamente refatorado.

Atualmente, ele possui uma interface própria desenvolvida exclusivamente para acesso pelo navegador. Essa arquitetura deve ser abandonada.

O Web Controller deve passar a funcionar apenas como um mecanismo de publicação de uma Custom Workspace existente do NodeStage.

Ao criar ou configurar um Web Controller, deve existir um campo para selecionar qual Custom Workspace será publicada.

Após essa seleção, o navegador deve renderizar exatamente essa workspace.

A representação visual deve ser idêntica à versão executada dentro do NodeStage, preservando integralmente:

* Layout.
* Identidade visual.
* Componentes.
* Organização.
* Estados visuais.
* Comportamento.
* Fluxo de interação.

Não deve existir uma interface web paralela, alternativa ou adaptada manualmente.

O navegador deve reutilizar a própria estrutura da Custom Workspace, em vez de possuir componentes específicos para o Web Controller.

A arquitetura deve ficar inteiramente baseada em Workspaces.

Isso deve permitir que o usuário crie uma Custom Workspace especificamente voltada para operação remota, utilizando somente os elementos desejados para controle pelo navegador.

Essa mesma Workspace deve continuar pertencendo ao sistema normal de Custom Workspaces do NodeStage e deve poder ser aberta normalmente dentro do programa no computador.

O Web Controller deve apenas publicar uma Workspace existente. Ele não deve ser responsável por construir, duplicar ou manter uma interface independente.

Toda a identidade visual do NodeStage deve permanecer consistente entre a aplicação desktop e o navegador.

Alterações feitas posteriormente na Custom Workspace selecionada devem ser refletidas na versão publicada pelo Web Controller, sem exigir a manutenção manual de uma interface web separada.

# Tarefa

Refatorar completamente o Web Controller para publicar Custom Workspaces.

## Contexto

O Web Controller atualmente possui uma interface própria e independente da aplicação principal.

Essa arquitetura gera uma implementação paralela para o navegador e exige que a interface web seja desenvolvida e mantida separadamente.

A Descrição Detalhada deste Card é a fonte canônica de todos os requisitos da tarefa. Não a substitua por interpretações livres e não remova requisitos durante a implementação.

## Objetivo

Transformar o Web Controller em um mecanismo de seleção, publicação e carregamento de uma Custom Workspace existente, exibindo no navegador a mesma Workspace utilizada dentro do NodeStage.

O resultado final deve eliminar a necessidade de criar e manter uma interface exclusiva para o Web Controller.

## Estado atual

O sistema atual possui uma interface própria para o Web Controller, com estrutura e componentes específicos para o ambiente web.

Antes de alterar o código, analisar:

* A implementação completa do Web Controller atual.
* O fluxo de criação e configuração do Web Controller.
* A estrutura utilizada para renderizar a interface no navegador.
* O sistema existente de Custom Workspaces.
* O carregamento, salvamento e identificação das Workspaces.
* Os componentes disponíveis dentro das Custom Workspaces.
* A comunicação entre os controles da interface e o estado real do NodeStage.
* As diferenças atuais entre a interface desktop e a interface web.
* Os pontos de duplicação entre os dois sistemas.
* As responsabilidades que podem ser removidas do Web Controller.
* Os pontos de integração necessários para publicar uma Workspace existente.

A refatoração não deve partir da suposição de que o sistema atual precisa ser preservado internamente. A implementação existente deve ser analisada, e a arquitetura paralela deve ser removida ou reorganizada conforme necessário para atingir o objetivo do Card.

## Requisitos funcionais

Implementar o Web Controller como um publicador de Custom Workspaces.

Ao criar ou editar a configuração de um Web Controller, disponibilizar a seleção de uma Custom Workspace existente.

A configuração deve manter a referência da Workspace selecionada utilizando o mecanismo de identificação e persistência compatível com o sistema real de Custom Workspaces encontrado no projeto.

Ao acessar o Web Controller pelo navegador, carregar a Custom Workspace configurada.

A Workspace publicada deve apresentar no navegador a mesma composição disponível dentro do NodeStage.

Os componentes presentes na Workspace devem continuar associados às funcionalidades reais correspondentes do programa.

O navegador deve permitir a interação com os elementos interativos presentes na Workspace publicada, respeitando o comportamento suportado pelo sistema de controle remoto.

A mesma Custom Workspace deve poder ser aberta dentro do NodeStage no computador.

O sistema deve permitir a criação de Workspaces organizadas especificamente para operação pelo navegador, tablet ou outro dispositivo remoto, sem transformá-las em um tipo separado de interface.

O Web Controller não deve definir manualmente quais painéis, botões, faders ou componentes serão exibidos. Essa definição deve vir da Custom Workspace selecionada.

A ordem, o posicionamento, o tamanho e a composição dos elementos devem vir da definição da Workspace.

A seleção da Workspace deve poder ser alterada posteriormente na configuração do Web Controller.

Após a alteração da Workspace selecionada, o navegador deve passar a carregar a nova Workspace configurada.

Alterações persistidas na Workspace selecionada devem ser utilizadas na próxima atualização ou carregamento da versão publicada, conforme o fluxo real de sincronização encontrado no projeto.

## Regras obrigatórias

A Custom Workspace deve ser a fonte canônica da interface publicada.

Não criar uma segunda definição de layout para o navegador.

Não criar um editor separado de Web Controller para reconstruir manualmente a mesma interface da Workspace.

Não manter dois conjuntos independentes de componentes para representar a mesma funcionalidade.

Não reinterpretar visualmente a Workspace como um painel web genérico.

Não substituir os componentes da Workspace por cards, widgets ou painéis web inventados.

Não criar uma identidade visual específica para o Web Controller.

Não alterar arbitrariamente nomes, hierarquia, dimensões, alinhamentos ou organização dos elementos ao publicar a Workspace.

Não remover elementos da Workspace apenas por ela estar sendo exibida no navegador, exceto quando uma limitação técnica real for identificada no código e tratada de forma explícita.

Não criar um novo tipo de Workspace exclusivamente web quando a Custom Workspace existente puder atender ao fluxo.

Não transformar o Web Controller em um construtor de interface.

O Web Controller deve manter somente as responsabilidades necessárias para:

* Selecionar a Workspace.
* Persistir a seleção.
* Publicar ou disponibilizar a Workspace.
* Carregar sua representação no navegador.
* Encaminhar as interações suportadas.
* Sincronizar os estados necessários.

A refatoração deve reduzir a duplicação entre desktop e navegador.

A mesma definição de Workspace deve alimentar os dois contextos.

## Interface e experiência de uso

O fluxo de configuração esperado é:

1. O usuário cria ou edita um Web Controller.
2. O sistema apresenta uma opção para escolher uma Custom Workspace.
3. O usuário seleciona uma Workspace existente.
4. A seleção é salva na configuração do Web Controller.
5. O usuário acessa o endereço correspondente no navegador.
6. O navegador carrega a Workspace selecionada.
7. A interface exibida representa a mesma Workspace utilizada pelo NodeStage.

A seleção deve utilizar os padrões visuais e de interação já existentes no NodeStage.

A lista de Workspaces deve apresentar somente itens válidos encontrados pelo sistema real de Custom Workspaces.

Quando nenhuma Workspace estiver selecionada, a configuração deve indicar claramente que o Web Controller ainda não possui uma interface publicada.

A aparência no navegador deve preservar, dentro das capacidades da implementação compartilhada:

* Tipografia.
* Cores.
* Bordas.
* Espaçamentos.
* Hierarquia visual.
* Dimensões relativas.
* Organização dos painéis.
* Estados ativos.
* Estados inativos.
* Estados de seleção.
* Estados de foco.
* Controles.
* Identidade visual geral.

Não criar uma versão simplificada apenas por estar no navegador.

A Workspace publicada pode ter sido organizada pelo usuário especificamente para controle remoto, mas essa organização deve ser feita no próprio sistema de Custom Workspaces.

## Arquitetura e integração

Analisar a arquitetura real antes de escolher a solução técnica.

O objetivo arquitetural é fazer com que o sistema de Custom Workspaces seja a definição única da interface.

Identificar quais partes da Workspace podem ser compartilhadas diretamente entre desktop e navegador e quais precisam de uma representação serializável, remota ou compatível com o ambiente web.

Caso seja necessária uma camada de representação intermediária, ela deve derivar diretamente da Workspace e não se tornar uma segunda fonte de verdade.

A estrutura intermediária, quando necessária, deve preservar:

* Identidade da Workspace.
* Identidade dos componentes.
* Hierarquia.
* Layout.
* Propriedades visuais.
* Ligações com funcionalidades.
* Estados necessários.
* Ações disponíveis.
* Ordem dos elementos.

Reaproveitar o sistema existente de persistência e identificação de Custom Workspaces.

Não inventar caminhos, arquivos, classes, módulos ou formatos sem primeiro verificar o código real.

O vínculo entre o Web Controller e a Workspace deve permanecer estável após reinicialização do NodeStage.

A configuração deve continuar válida enquanto a Workspace selecionada existir.

O sistema deve impedir que o Web Controller mantenha silenciosamente uma cópia antiga e desconectada da Workspace original.

Quando a Workspace for atualizada, o Web Controller deve utilizar sua definição atual persistida.

A comunicação remota deve continuar utilizando os mecanismos existentes do Web Controller quando forem compatíveis com a nova arquitetura.

Partes antigas responsáveis apenas pela interface própria devem ser removidas, desativadas ou refatoradas para não permanecerem como uma arquitetura paralela.

Não manter código legado sem uso apenas para preservar a interface anterior.

A implementação deve considerar que uma Workspace pode conter diferentes tipos de componentes disponíveis no sistema atual.

A arquitetura deve ser extensível para que novos componentes adicionados ao sistema de Custom Workspaces possam ser publicados sem exigir a criação manual de uma nova tela exclusiva no Web Controller.

## Tratamento de estados e erros

Tratar a ausência de uma Workspace selecionada.

Tratar uma referência de Workspace que não possa mais ser resolvida.

Tratar uma Workspace removida após ter sido configurada no Web Controller.

Tratar falhas de carregamento da definição da Workspace.

Tratar dados inválidos ou incompletos sem derrubar o Web Controller ou o restante do NodeStage.

Tratar componentes que não possam ser representados ou utilizados no navegador.

Nesses casos, não substituir automaticamente o componente por uma interface inventada.

A falha deve ser identificável e tratada de forma consistente com o sistema existente.

Evitar que um único componente inválido impeça toda a Workspace de ser carregada quando for tecnicamente possível isolar a falha.

Tratar indisponibilidade temporária de comunicação entre navegador e NodeStage.

Quando a comunicação for restabelecida, recuperar os estados conforme os mecanismos reais do projeto.

Evitar duplicação de ações durante reconexões.

Tratar mudança da Workspace configurada enquanto o Web Controller estiver aberto.

Definir o comportamento de atualização com base na arquitetura existente, garantindo que o navegador não permaneça indefinidamente exibindo uma Workspace que não é mais a selecionada.

Tratar múltiplos navegadores conectados ao mesmo Web Controller sem criar definições divergentes da interface.

## Restrições

Não criar um novo painel web independente.

Não redesenhar a interface para parecer um dashboard genérico.

Não criar componentes exclusivos para o navegador quando já existir uma definição equivalente na Custom Workspace.

Não duplicar manualmente o layout.

Não criar dois editores separados.

Não alterar o sistema de Custom Workspaces sem necessidade comprovada pela integração.

Não quebrar o carregamento das Custom Workspaces dentro do NodeStage.

Não impedir que uma Workspace publicada seja aberta e utilizada no computador.

Não limitar a Custom Workspace a uso exclusivo pelo Web Controller.

Não remover funcionalidades existentes do sistema geral de Workspaces.

Não inventar compatibilidade, componentes ou comportamentos que não existam no código.

Não declarar a tarefa concluída mantendo a interface antiga como caminho principal.

Não deixar o sistema novo dependendo da manutenção simultânea da interface própria antiga.

## Critérios de aceitação

A tarefa será aceita quando:

* A configuração do Web Controller permitir selecionar uma Custom Workspace existente.
* A seleção permanecer salva após reiniciar o NodeStage.
* O navegador carregar a Workspace selecionada.
* A definição visual utilizada pelo navegador vier da Custom Workspace.
* A mesma Workspace puder ser aberta dentro do NodeStage.
* O layout exibido no navegador corresponder à organização da Workspace.
* Os componentes suportados manterem seus comportamentos e vínculos funcionais.
* Não existir necessidade de reconstruir manualmente a mesma interface em um painel web separado.
* A interface antiga deixar de ser a fonte principal do Web Controller.
* A troca da Workspace configurada alterar a interface publicada.
* A remoção ou indisponibilidade da Workspace for tratada sem falha global.
* A arquitetura não mantiver duas fontes independentes de verdade para a mesma interface.
* Novas Workspaces puderem ser publicadas sem criação manual de uma nova tela web.
* A identidade visual permanecer consistente com o NodeStage.
* A refatoração não quebrar o funcionamento normal das Custom Workspaces no desktop.

## Instrução de execução

Antes de implementar qualquer alteração, localizar e analisar o código real do Web Controller e do sistema de Custom Workspaces.

Mapear:

* Fluxo atual de criação e configuração.
* Persistência atual.
* Componentes de interface.
* Sistema de layout.
* Comunicação remota.
* Sincronização de estado.
* Renderização desktop.
* Renderização web.
* Dependências entre módulos.
* Código exclusivo da interface web atual.
* Possibilidades reais de reaproveitamento.

Depois da análise, definir a menor arquitetura compartilhada capaz de tornar a Custom Workspace a fonte única da interface.

Implementar a refatoração de forma completa, removendo a dependência da interface web própria.

Validar o fluxo completo:

* Criar ou abrir uma Custom Workspace.
* Configurar essa Workspace em um Web Controller.
* Abrir o navegador.
* Conferir a correspondência visual e estrutural.
* Interagir com os componentes suportados.
* Reiniciar o programa.
* Confirmar persistência.
* Alterar a Workspace.
* Confirmar atualização.
* Remover ou invalidar a Workspace.
* Confirmar tratamento de erro.
* Abrir a mesma Workspace no desktop.
* Confirmar que o funcionamento normal foi preservado.

Não inventar detalhes técnicos ausentes. Utilizar os nomes, arquivos, classes, estruturas e padrões encontrados no projeto.
