# TASK-0013 — Implementar sistema de Group Types no Live Workspace

## Summary

Permitir que cada Group assuma um Type operacional que adapte sua interface, seus controles e seu comportamento à função exercida no Live Workspace.

## Detailed Description

<!-- task-board:description:start -->
Implementar no NodeStage um sistema de **Group Types** que permita definir e alterar o Type operacional de cada Group existente no Live Workspace.

Atualmente, os Groups funcionam como contêineres genéricos de clips. O novo sistema deve manter essa estrutura, mas permitir que cada Group adapte sua interface, seus controles disponíveis e seu comportamento operacional conforme a finalidade escolhida.

O Type deve ser uma propriedade persistente do próprio Group. A seleção deve ficar disponível nas propriedades ou configurações do Group por meio de uma lista clara de Types.

O sistema deve incluir inicialmente:

* `Standard`
* `Camera`
* `Overlay`
* `Media`
* `Audio`
* `Lighting`
* `Generator`
* `Router`
* `Playlist`

O Type `Standard` representa o comportamento genérico atual. Groups existentes sem Type salvo devem ser carregados automaticamente como `Standard`, preservando o funcionamento atual dos projetos.

Alterar o Type deve transformar o comportamento e a apresentação do mesmo Group. A operação não pode:

* criar outro Group;
* apagar clips;
* mover o Group para outra Collection;
* alterar sua ordem;
* perder nome, identificador ou estado persistido;
* remover configurações que continuem compatíveis;
* quebrar referências, automações, atalhos, MIDI, macros ou integrações existentes.

O Type não deve funcionar apenas como nome, cor ou ícone. Ele deve determinar quais controles, ações, indicadores e formas de apresentação são relevantes para aquele Group.

### Type `Standard`

Deve manter o comportamento atual de um Group comum, servindo como compatibilidade padrão e opção neutra.

Controles esperados:

* intensidade ou opacidade;
* ativação;
* seleção de clips;
* reprodução;
* transições;
* propriedades gerais já disponíveis.

### Type `Camera`

Deve transformar o Group em uma estrutura operacional semelhante a um switcher de vídeo.

O objetivo é permitir que os clips ou fontes do Group sejam tratados como entradas de câmera, com seleção rápida e leitura clara do estado ativo.

Controles e estados previstos:

* seleção direta de câmera ou fonte;
* identificação da câmera ativa;
* controles `CUT` e `AUTO`;
* configuração ou seleção de transição;
* indicação de Preview e Program quando esses estados estiverem disponíveis;
* tally ou indicação visual equivalente;
* estado de disponibilidade do sinal;
* interface priorizando operação rápida em vez de gerenciamento genérico de mídia.

O sistema deve reaproveitar a lógica real de disparo, seleção e transição existente no Live Workspace. Não deve criar um segundo mecanismo independente de switch, playback ou transição.

### Type `Overlay`

Deve adaptar o Group para conteúdos como logos, lower thirds, bugs, identificações e demais elementos de sobreposição.

Controles e estados previstos:

* mostrar;
* ocultar;
* fade de entrada e saída;
* opacidade;
* auto-hide;
* prioridade de exibição;
* identificação clara de overlay ativo.

O comportamento deve continuar integrado à composição real do Live Workspace, sem criar uma camada de renderização paralela apenas para esse Type.

### Type `Media`

Deve manter foco em vídeos e imagens reproduzidos como conteúdo principal.

A apresentação pode priorizar:

* thumbnails;
* reprodução;
* pausa;
* posição atual;
* duração;
* carregamento;
* disponibilidade da mídia;
* seleção e troca de clips;
* indicadores relacionados a cache ou pré-carregamento quando essas informações já existirem no sistema.

### Type `Audio`

Deve adaptar o Group para operação de conteúdos de áudio.

Controles e estados previstos:

* volume;
* mute;
* solo;
* reprodução;
* pausa;
* estado do áudio;
* medidor de nível quando o sistema possuir dados reais para isso.

Não criar medidores simulados ou estados exclusivamente visuais sem conexão com o áudio real.

### Type `Lighting`

Deve preparar o Group para conteúdos, cues ou ações relacionados à iluminação e às futuras integrações DMX/Art-Net.

A primeira implementação não precisa criar um novo sistema de iluminação caso ele ainda não exista. O Type deve ser estruturado para receber controles específicos de intensidade, cues, paletas ou equipamentos quando esses recursos estiverem disponíveis.

Enquanto não houver integração funcional correspondente, o Type não deve exibir controles falsos ou ações sem implementação real.

### Type `Generator`

Deve adaptar o Group para fontes e conteúdos procedurais.

Controles previstos:

* intensidade;
* ativação;
* play e pause quando aplicável;
* acesso rápido aos parâmetros principais expostos pelo procedural;
* indicação de execução ou pausa.

Os parâmetros rápidos devem vir das propriedades reais da fonte procedural, evitando listas fixas desconectadas do conteúdo selecionado.

### Type `Router`

Deve adaptar o Group para funções de roteamento e direcionamento de sinal.

A interface deve priorizar:

* origem;
* destino;
* estado da rota;
* ativação;
* acesso às propriedades de roteamento.

Não duplicar a lógica de Router Nodes ou demais sistemas de roteamento existentes. O Type deve integrar e apresentar os recursos reais já disponíveis.

### Type `Playlist`

Deve adaptar o Group para reprodução sequencial de clips.

Controles e estados previstos:

* play;
* pause;
* próximo;
* anterior;
* loop;
* shuffle;
* item atual;
* próximo item;
* tempo restante quando disponível;
* avanço automático quando configurado.

A ordem da playlist deve respeitar a ordem real dos clips do Group ou a estrutura de ordenação já existente no projeto.

### Interface do Group

A apresentação do Group deve reagir ao Type selecionado.

Essa adaptação pode atingir:

* botões rápidos;
* indicadores;
* informações exibidas;
* destaque de estados;
* organização interna;
* atalhos contextuais;
* controles apresentados no Group;
* propriedades exibidas no modal ou Inspector;
* controles disponibilizados para outras superfícies, incluindo a futura janela `Control Surface`.

O Group deve continuar visualmente reconhecível como parte da mesma interface do NodeStage. Não criar nove interfaces completamente isoladas ou inconsistentes entre si.

Todos os Types devem compartilhar uma base visual comum, adicionando ou priorizando somente os controles necessários para cada função.

### Edição do Type

A troca de Type deve estar disponível nas propriedades ou configurações do Group.

O seletor deve:

* mostrar o Type atual;
* listar os Types disponíveis;
* permitir troca direta;
* deixar claro quando a alteração muda os controles apresentados;
* atualizar a interface imediatamente;
* persistir a escolha no projeto.

Ao trocar de Type, parâmetros exclusivos do Type anterior não devem ser aplicados indevidamente ao novo Type. Dados que possam ser reutilizados futuramente não devem ser apagados sem necessidade.

Ao retornar a um Type usado anteriormente, configurações específicas ainda válidas podem ser restauradas, desde que isso seja compatível com o modelo atual de persistência do projeto.

### Arquitetura extensível

O sistema deve permitir adicionar novos Group Types futuramente sem espalhar condicionais específicas por toda a interface.

A definição de um Type deve concentrar, conforme a arquitetura real encontrada:

* identificador estável;
* nome exibido;
* controles disponíveis;
* ações;
* indicadores;
* regras de apresentação;
* recursos compatíveis;
* parâmetros específicos;
* comportamento padrão.

A implementação deve reutilizar os modelos de Group, comandos, eventos, componentes visuais, playback, transições, persistência e sincronização já existentes.

A diferença entre os Types deve ser configurada ou registrada em uma estrutura central compatível com a arquitetura atual. Não criar uma arquitetura paralela de Groups.

### Fonte única de verdade

O Type e seus controles devem operar sobre o mesmo estado real utilizado pelo Live Workspace.

Alterações feitas por:

* Group;
* modal de propriedades;
* Inspector;
* Control Surface;
* MIDI;
* atalhos;
* macros;
* automações;
* controle remoto futuro;

devem permanecer sincronizadas.

Não manter cópias independentes de intensidade, seleção, mute, solo, playback ou estado de transição dentro da interface específica de cada Type.

### Persistência e compatibilidade

O Type selecionado deve ser salvo junto ao Group no projeto.

Projetos anteriores devem continuar abrindo normalmente. Quando o campo de Type não existir, o sistema deve assumir `Standard`.

O carregamento deve tratar:

* Type ausente;
* Type desconhecido;
* Type removido em uma versão futura;
* dados específicos incompletos;
* Group vazio;
* Group com mídia incompatível com o Type selecionado.

Quando o Type salvo for desconhecido ou inválido, o Group deve usar `Standard` sem impedir a abertura do projeto. O dado original não deve ser destruído silenciosamente caso ainda possa ser preservado para recuperação.

A seleção de um Type não deve restringir obrigatoriamente os conteúdos que podem existir no Group. Ela define seu comportamento operacional e sua apresentação. Restrições rígidas de conteúdo só podem ser adicionadas se já existirem regras equivalentes no NodeStage ou se forem necessárias para impedir uma operação tecnicamente inválida.

### Desempenho

A adaptação visual por Type não deve reconstruir toda a interface a cada frame.

Atualizações devem ocorrer quando houver:

* mudança de Type;
* alteração relevante do Group;
* mudança no conteúdo ativo;
* alteração de playback;
* alteração de sinal;
* mudança em parâmetros exibidos.

Indicadores animados ou medidores devem utilizar dados reais e frequência de atualização controlada.

# Tarefa

Implementar sistema de Group Types no Live Workspace

## Contexto

Os Groups atuais são genéricos. A Descrição Detalhada deste Card é a fonte canônica dos requisitos para transformá-los em estruturas operacionais adaptáveis por Type, sem substituir o sistema atual de Groups.

## Objetivo

Adicionar uma propriedade persistente de Type aos Groups e fazer com que interface, controles, ações e indicadores se adaptem à função escolhida, preservando a estrutura, os conteúdos e todas as integrações existentes.

## Estado atual

Antes de alterar o código, audite a implementação real de:

* Groups e Collections;
* criação, edição, remoção, ordenação e persistência de Groups;
* interface do Live Workspace;
* modal e Inspector de Group;
* seleção e disparo de clips;
* playback e transições;
* intensidade, opacidade, mute e solo;
* comandos, eventos, atalhos, MIDI, macros e automações;
* serialização e migração de projetos;
* componentes reutilizáveis de botões, faders, estados e indicadores;
* Control Surface, caso já esteja implementada.

Identifique quais comportamentos já existem e podem ser apenas reorganizados ou expostos conforme o Type. Não presuma nomes de arquivos, classes ou formatos de persistência sem verificar o projeto.

## Requisitos funcionais

Implemente integralmente a Descrição Detalhada, tratando-a como registro canônico e não duplicando sistemas já existentes.

Organize a execução em etapas:

1. introduzir o Type no modelo real de Group;
2. garantir carregamento compatível de projetos anteriores;
3. disponibilizar edição do Type;
4. criar o registro central dos Types;
5. adaptar a apresentação do Group;
6. conectar controles específicos aos comandos reais;
7. integrar propriedades, Inspector e superfícies de controle;
8. validar persistência e sincronização;
9. validar todos os Types iniciais;
10. remover somente duplicações comprovadamente substituídas.

## Regras obrigatórias

* `Standard` deve preservar o comportamento atual.
* Groups antigos sem Type devem assumir `Standard`.
* Trocar o Type deve modificar o Group existente, não substituí-lo.
* Nenhum clip, vínculo, ordem ou configuração compatível pode ser perdido.
* Todo controle deve executar uma ação real do NodeStage.
* Não criar estados visuais falsos.
* Não duplicar playback, transições, roteamento, áudio, Groups ou Collections.
* O Type deve ser persistente e possuir identificação estável.
* A arquitetura deve aceitar novos Types sem condicionais espalhadas.
* Tipos desconhecidos devem possuir fallback seguro para `Standard`.
* O sistema deve manter uma única fonte de verdade.
* Alterações devem respeitar os padrões visuais e arquitetônicos encontrados no código real.

## Interface e experiência de uso

Use a interface atual do NodeStage como referência visual.

O seletor de Type deve ficar na área real de configuração do Group que melhor corresponda ao padrão existente. Não criar um fluxo isolado se o modal ou Inspector atual já comportar essa propriedade.

A mudança deve atualizar imediatamente:

* identificação do Type;
* controles rápidos;
* indicadores;
* propriedades contextuais;
* apresentação operacional do Group.

Mantenha controles comuns em posições consistentes entre os Types. Controles específicos devem aparecer somente quando forem funcionais e relevantes.

Valide o uso em Groups:

* vazios;
* com muitos clips;
* recolhidos;
* selecionados;
* ativos;
* inativos;
* dentro de diferentes Collections;
* exibidos em diferentes modos do Live Workspace.

## Arquitetura e integração

Parta da arquitetura existente.

Defina uma responsabilidade central para registrar ou resolver as capacidades de cada Type, sem criar uma nova implementação completa de Group.

A camada de Type deve descrever ou fornecer os controles e comportamentos contextuais, enquanto os modelos e serviços atuais continuam responsáveis pelo estado real.

Integre o Type com:

* serialização do projeto;
* carregamento e migração;
* comandos de Group;
* sistema de eventos;
* atualização de UI;
* modais e Inspectors;
* Control Surface;
* atalhos e controles externos quando estes já consumirem dados de Group.

Caso o projeto já possua registries, descriptors, factories ou sistemas equivalentes, reutilize o padrão existente em vez de introduzir uma abstração concorrente.

## Tratamento de estados e erros

Implemente tratamento determinístico para:

* ausência do campo de Type;
* valor vazio;
* identificador desconhecido;
* falha ao carregar dados específicos;
* Group sem clips;
* mídia indisponível;
* fonte de câmera desconectada;
* áudio sem medição disponível;
* procedural sem parâmetros expostos;
* Router sem origem ou destino;
* Playlist sem próximo item;
* recurso específico ainda não implementado.

Nesses casos:

* mantenha o Group utilizável;
* evite travamentos;
* não exiba ações falsas;
* apresente estado indisponível quando necessário;
* preserve dados recuperáveis;
* use `Standard` como fallback somente para o comportamento, sem destruição silenciosa dos dados originais.

## Restrições

* Não redesenhar todo o Live Workspace.
* Não transformar Group Types em Workspaces separados.
* Não criar subclasses independentes com cópias completas do Group sem necessidade arquitetônica comprovada.
* Não impedir projetos antigos de abrir.
* Não apagar dados específicos ao alternar Types.
* Não vincular a implementação exclusivamente à Control Surface.
* Não criar funcionalidades completas de DMX, Art-Net, áudio ou roteamento que não façam parte dos sistemas existentes.
* Não simular tally, medidores, Preview, Program ou disponibilidade de sinal.
* Não alterar comportamentos globais de playback e transição fora do necessário para expô-los ao Type.
* Não remover código antigo antes de confirmar equivalência funcional.
* Não inventar nomes de classes, arquivos, caminhos ou formatos de dados.

## Critérios de aceitação

A implementação será aceita quando:

* qualquer Group puder ter seu Type consultado e alterado;
* os nove Types iniciais estiverem registrados;
* `Standard` reproduzir o comportamento anterior;
* a troca ocorrer sem recriar ou danificar o Group;
* a interface reagir imediatamente ao Type;
* os controles exibidos estiverem conectados a funcionalidades reais;
* projetos antigos abrirem como `Standard`;
* projetos novos preservarem o Type após salvar e reabrir;
* Types inválidos não impedirem o carregamento;
* múltiplas interfaces refletirem o mesmo estado;
* novos Types puderem ser acrescentados sem alterações distribuídas por todo o Live Workspace;
* não houver regressão em Groups, Collections, clips, transições, atalhos, MIDI, macros ou automações existentes.

## Instrução de execução

Analise primeiro o código real, o Code Registry e a documentação relacionada. Registre o fluxo atual antes de alterar o modelo ou a persistência.

Implemente de forma incremental, começando pelo modelo, compatibilidade e `Standard`. Em seguida, conecte os demais Types aos recursos reais já disponíveis.

Quando um recurso descrito ainda não existir funcionalmente no NodeStage, prepare a capacidade de integração sem criar controles falsos ou expandir o escopo para implementar o sistema ausente.

Ao concluir, valide carregamento de projetos antigos e novos, troca repetida entre Types, persistência, sincronização entre interfaces e ausência de regressões.
