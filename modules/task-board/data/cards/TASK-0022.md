# TASK-0022 — Adicionar Browser Source interativo vinculado ao Node

## Summary

Permitir carregar uma página web por URL como conteúdo de um Node, com navegação interativa controlada nos fluxos de Build e Live.

## Detailed Description

<!-- task-board:description:start -->
Implementar no NodeStage uma fonte de navegador equivalente ao Browser Source do OBS, permitindo carregar e renderizar uma página web a partir de um link informado pelo usuário.

A página web deve permanecer vinculada ao Node que a criou. Cada Node de navegador deve manter sua própria URL, estado e instância de conteúdo, sem compartilhar ou transferir automaticamente a navegação para outros Nodes.

No Build, a página deve ser exibida no Preview do Node. A interação direta com o navegador deve permanecer desativada por padrão para que cliques e movimentos do mouse continuem sendo utilizados normalmente pela interface do NodeStage.

O Preview deve possuir um botão com o label literal Press to navigate. Ao ativar esse botão, a área do Preview deve entrar em modo de navegação e encaminhar para a página web as interações necessárias de mouse e teclado, permitindo clicar em links, botões, campos, menus, rolar a página e utilizar os demais controles interativos oferecidos pelo site.

Deve existir uma forma clara de sair do modo de navegação e devolver o controle do mouse e do teclado à interface normal do NodeStage. A IA deve localizar no repositório o padrão existente mais próximo para modos temporários de interação e utilizar a menor solução compatível com a arquitetura encontrada, sem criar atalhos ou novos padrões globais desnecessários.

No Live, o conteúdo web deve poder ser utilizado como qualquer outra fonte compatível do Live. A navegação não deve ocorrer diretamente sobre o deck ou sobre a operação normal da interface. Para interagir com a página, o usuário deve abrir o modal correspondente ao conteúdo ou Node de navegador.

Dentro desse modal, deve existir o botão Press to navigate, com o mesmo comportamento do Preview do Build. Enquanto o modo estiver desativado, o mouse e o teclado devem continuar controlando a interface do modal e do NodeStage. Enquanto estiver ativado, as interações realizadas sobre a área do navegador devem ser encaminhadas à página carregada.

A URL configurada, as configurações necessárias da fonte e sua associação ao Node devem ser persistidas com o projeto pelo mecanismo já utilizado pelo NodeStage. Ao reabrir o projeto, o Node deve restaurar a página configurada sem exigir que o usuário informe novamente o link.

A implementação deve contemplar, sem inventar novos fluxos de produto:

* criação ou seleção da fonte de navegador no fluxo de Nodes;
* campo para informar e alterar a URL;
* carregamento visual da página dentro do NodeStage;
* renderização contínua da página no pipeline visual;
* interação de mouse, rolagem e teclado quando o modo Press to navigate estiver ativo;
* isolamento entre múltiplos Nodes de navegador;
* atualização do conteúdo visual quando a página mudar;
* redimensionamento da página de acordo com a área ou resolução atribuída à fonte;
* liberação correta dos recursos quando o Node, conteúdo ou projeto for fechado;
* tratamento de URL vazia, inválida ou indisponível;
* indicação visual objetiva de carregamento ou falha, utilizando padrões já existentes no NodeStage;
* preservação do último conteúdo visual válido quando uma falha temporária não exigir a destruição imediata da instância;
* prevenção de travamento da interface principal durante carregamentos, redirecionamentos ou páginas lentas.

O comportamento deve tomar como referência funcional a importação de navegador do OBS, especialmente na separação entre renderização da página e modo explícito de interação. A referência ao OBS não autoriza copiar identidade visual, nomenclaturas adicionais, configurações ou recursos que não tenham sido solicitados.

A IA deve investigar se o NodeStage já possui infraestrutura de navegador embutido, Web Controller, visualização HTML, renderização web ou alguma dependência compatível. A implementação deve reaproveitar a arquitetura existente quando aplicável. Não deve introduzir silenciosamente um novo framework, biblioteca ou mecanismo de navegador sem antes confirmar que não existe solução equivalente no repositório.

Decisões não especificadas, como resolução padrão, taxa de atualização, suporte a áudio da página, transparência, user agent, cache, cookies, armazenamento de sessão, permissões, scripts personalizados, CSS personalizado e comportamento de recarregamento, não devem ser inventadas. A IA deve procurar padrões equivalentes no código e preservar o comportamento atual. Quando não existir decisão derivável da arquitetura, registrar como pendência no relatório final em vez de expandir o escopo.

## Detailed AI Prompt

<!-- task-board:ai-prompt:start -->
Tarefa

Adicionar Browser Source interativo vinculado ao Node

Contexto

O NodeStage precisa carregar páginas web como fontes visuais vinculadas a Nodes, seguindo a lógica de renderização e interação explícita utilizada pelo Browser Source do OBS.

Objetivo

Implementar integralmente o comportamento definido na Descrição Detalhada, integrando a fonte de navegador aos fluxos existentes de Build, Live, Preview, modal, renderização e persistência sem comprometer a operação normal da interface.

Estado atual e investigação

Antes de alterar o código:

1. Mapear como os tipos atuais de Node e fontes visuais são registrados, criados, serializados, renderizados e destruídos.
2. Localizar os proprietários atuais do Preview do Build e dos modais de conteúdo do Live.
3. Identificar como o sistema diferencia interação da interface, interação com previews e captura temporária de mouse ou teclado.
4. Localizar o pipeline responsável por fornecer textura, frame ou saída visual de uma fonte para o restante do NodeStage.
5. Investigar infraestrutura existente relacionada a HTML, navegador embutido, Web Controller, conteúdo web ou dependências capazes de renderizar páginas.
6. Mapear o sistema atual de persistência de propriedades de Nodes e restauração de projetos.
7. Verificar como fontes lentas, indisponíveis ou assíncronas são tratadas sem bloquear a interface principal.
8. Identificar o padrão atual de mensagens visuais para carregamento, conteúdo indisponível e erro.

Não assumir nomes de classes, serviços, arquivos ou bibliotecas antes dessa análise.

Estratégia de integração e regras

Utilizar a Descrição Detalhada como fonte canônica dos requisitos.

Integrar a fonte de navegador ao mesmo contrato utilizado pelas demais fontes visuais sempre que isso for compatível com a arquitetura encontrada. Separar claramente:

* configuração e persistência da fonte;
* ciclo de vida da instância de navegador;
* produção do frame visual;
* apresentação no Preview e no Live;
* encaminhamento temporário de eventos de interação;
* estado do modo Press to navigate;
* tratamento de carregamento e falhas.

Garantir que o estado interativo pertença à visualização que está sendo operada e não transforme globalmente o mouse ou o teclado do aplicativo. A ativação e a saída do modo de navegação devem realizar captura e liberação limpas, inclusive ao fechar modal, trocar seleção, remover Node, mudar de workspace ou encerrar projeto.

Manter instâncias e estados isolados por Node. Não utilizar uma única instância global de navegador se isso provocar compartilhamento de URL, sessão visual, navegação ou ciclo de vida entre conteúdos independentes.

Reaproveitar os mecanismos existentes de invalidação, atualização de textura, dimensionamento, serialização e gerenciamento de recursos. Evitar criar caminhos paralelos quando já houver contratos equivalentes no sistema.

Não realizar refatorações amplas fora das responsabilidades diretamente necessárias. Alterações estruturais indispensáveis devem ser mínimas, justificadas e registradas no relatório final.

Validação e tratamento de erros

Validar objetivamente:

* criação de uma fonte de navegador;
* carregamento de uma URL válida;
* exibição no Preview do Build;
* exibição como conteúdo no Live;
* ativação e desativação de Press to navigate;
* clique, rolagem, foco de campos e entrada de teclado;
* retorno do controle à interface do NodeStage;
* persistência e restauração da URL;
* isolamento entre pelo menos dois Nodes com URLs ou navegações diferentes;
* redimensionamento da área de renderização;
* remoção e recriação da fonte;
* fechamento do modal durante o modo de navegação;
* troca de workspace durante carregamento;
* URL vazia;
* URL inválida;
* endereço indisponível;
* página lenta;
* redirecionamento;
* falha temporária após uma página já ter sido carregada;
* encerramento do projeto sem recursos ou capturas de entrada pendentes.

Quando houver infraestrutura de testes automatizados compatível, adicionar testes para persistência, isolamento de estado e ciclo de vida. Os fluxos de renderização e interação devem também ser verificados manualmente no Build e no Live.

Falhas de carregamento não podem bloquear a interface principal, deixar captura de mouse ou teclado ativa, acessar instâncias destruídas ou provocar encerramento do NodeStage.

Restrições de escopo

Não transformar o NodeStage em um navegador completo.

Não adicionar recursos não solicitados, incluindo controles avançados de navegação, extensões, favoritos, histórico global, ferramentas de desenvolvedor, scripts personalizados, CSS personalizado, autenticação especial ou gerenciamento próprio de downloads.

Não alterar o comportamento das demais fontes, Nodes, previews ou modais além do necessário para integrar este novo tipo.

Não definir silenciosamente comportamentos de áudio, transparência, cookies, cache, resolução padrão ou taxa de atualização. Derivar essas decisões dos padrões existentes ou registrá-las como pendências reais.

Não copiar identidade visual ou recursos adicionais do OBS. Utilizar o OBS apenas como referência funcional para Browser Source e interação explícita.

Instrução de execução e relatório

Analisar o código real antes de escolher a solução. Implementar a menor integração coerente com a arquitetura existente, sem substituir mecanismos funcionais por sistemas paralelos.

Ao concluir, apresentar relatório objetivo contendo:

* diagnóstico do estado encontrado;
* infraestrutura web ou de navegador já existente;
* arquivos alterados;
* decisões arquiteturais adotadas;
* comportamentos implementados;
* tratamento do ciclo de vida e da captura de entrada;
* testes automatizados executados;
* validações manuais realizadas no Build e no Live;
* regressões verificadas;
* limitações reais ou decisões pendentes;
* atualização de VERSION;
* atualização de CHANGELOG.md;
* atualização dos registros obrigatórios do projeto no Code Registry.

## Expected Features

<!-- task-board:expected-features:start -->
* Uma URL pode ser carregada como fonte visual vinculada a um Node.
* O conteúdo web aparece no Preview do Build e no fluxo visual do Live.
* O botão Press to navigate permite interagir com a página no Preview do Build.
* O botão Press to navigate permite interagir com a página pelo modal no Live.
* Fora do modo de navegação, mouse e teclado continuam controlando normalmente o NodeStage.
* O modo de navegação pode ser encerrado sem deixar captura de entrada ativa.
* Cada Node mantém sua própria URL, navegação e instância de conteúdo.
* A URL e a associação com o Node são restauradas ao reabrir o projeto.
* URLs inválidas, indisponíveis ou lentas não bloqueiam nem encerram o NodeStage.
* Remover ou fechar a fonte libera corretamente seus recursos.
